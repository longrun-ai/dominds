# Software Defined Harness：由 DSL 定义运行环境

英文版：[English](./software-defined-harness.md)

## 决策与现状

保留微内核，取消以 **Dominds App、App 组合根和 App composition revision** 为目标的设计。新的方向是 **Software Defined Harness**：整个运行环境由 DSL 程序定义，扩展组件向运行时提供 DSL 可用能力；编排智能体通过演进 DSL 脚本，主导设计各执行智能体的行为和交互。

这是目标方向，不是已经实现的 DSL。`DomindsApp`、App Host IPC、安装命令、`.minds/team.yaml` 和现有对话机制仍是当前接口，须逐步迁移。沿袭的是这些实现服务的业务价值，不是它们偶然形成的类型、目录或组合模型。

## 从第一性原则沿袭价值

要解决的问题是：执行环境如何随任务经验演进，而不要求每次协作方式改变都修改 Dominds 内部代码。编排者需要能改变分工、上下文、能力授予、交互、接续和交付规则；执行者需要明确的任务与能力边界；人类需要理解、纠正和追踪这些变化。

| 已有价值        | 新设计必须保持的可观察结果                                           |
| --------------- | -------------------------------------------------------------------- |
| 分工与专注      | 可以分派、等待、追问和汇总；执行者只接收职责所需的上下文             |
| 长程接续        | 中断、重启或清理上下文后，任务、结果和回复责任仍能正确接续           |
| 能力边界        | DSL、智能体和组件不能绕过授权；安装、导入不自动扩大权限              |
| 人类参与        | 等待回答、接收回答、停止与继续是可追踪的业务状态                     |
| rtws 隔离与透明 | 脚本、配置、记忆和执行证据可检查、可版本管理，运行状态按 rtws 隔离   |
| 纠错与可解释性  | 可以说明哪版脚本、哪个执行者、哪次动作导致结果，并判断失败后怎样继续 |

每项抽象必须连接业务场景、必要约束、旧实现中要继承的价值和验收证据。业务关切与组件可以是多对多关系；不能把表格行直接转为组件、DSL 原语或通用类型。不以结构对称、通用框架或推测性微观优化作为收益。

## 职责边界

**微内核**提供通用执行基础：运行身份和隔离、受控能力调用、持久化事实、事件投递、对话驱动以及中断恢复。具体边界由业务不变量证明；不为了缩小代码体积把完整性约束移到可绕过的脚本中。

**Harness DSL**是运行环境的程序，定义执行者的创建和职责、输入与上下文、能力绑定、消息和结果流转、并行与等待、失败处置、人类交互，以及环境启动和演进。它不局限于静态 team 配置、工具列表或一张预设流程图。

**扩展组件**实现 DSL 可用能力，例如浏览器会话、外部系统交互、协作协议、领域规则和界面。组件实现能力，DSL 编排其使用。安装、发现、导入、授予和调用是不同动作；组件不因安装取得运行主权，也不成为换名后的 App 组合根。

能力契约只需声明足以检查调用和恢复的输入、输出、事件、权限、副作用及失败/重试语义。涉及持久化或外部副作用时，要说明去重依据、可恢复条件和不确定结果的处置。纯计算能力不必实现无关的生命周期框架。

## 编排者如何演进环境

1. 从任务和运行证据提出行为改变，说明收益及受影响的已有价值。
2. 修改 rtws 中的 DSL 脚本，形成候选版本。
3. 校验语法、能力引用和当前权限，在隔离环境执行相应业务场景。
4. 经微内核控制的激活路径采用新版本，激活本身仍受现行授权约束。
5. 根据执行证据继续调整；失败时能恢复已知脚本版本，并明确运行状态怎样处置。

动作要归属于确定的脚本版本。更新不能让未完成动作悄悄换用另一版规则，应明确选择等待完成、取消、继续按旧版执行或受支持的迁移。回退脚本不会撤销已发生的外部副作用。

这是程序演进路径，不沿用 App composition root 模型。是否需要内部计划表示、哪些状态可迁移，由首批场景证明；现在不冻结通用编译器或任意热更新平台。

## 以三个场景确定最小语义

### 执行与复核

编排者收到需求，派执行者完成改动，再派复核者检验结果；不通过则把具体反馈交回执行者，通过才交付。验收角色和上下文隔离、能力授予、结果归属、受业务条件约束的循环，以及失败时不提前交付。

以下仅是语义讨论用的伪代码，**不是可执行语法或语言选择**：

```text
on request_received(request):
    builder = agents.start(role="implement", context=request,
                           grants=[workspace.edit])
    checker = agents.start(role="review", grants=[workspace.read])
    result = await messages.result(builder)
    verdict = await review.check(checker, request, result)
    while verdict.needs_changes:
        result = await messages.ask(builder, verdict.feedback)
        verdict = await review.check(checker, request, result)
    deliver(result, evidence=verdict)
```

能力名称不预先决定组件划分。异常、取消、循环的停止条件和重启语义还须通过可执行试验确定。

### 并行工作、等待人类与恢复

编排者并行安排实现和调查。调查需要人类确认时暂停对应工作，另一执行者仍可继续。结果回传中进程重启，确认答案和已完成工作不能丢失，结果不能重复消费；人类明确停止的任务不能自行重启。

验收任务关联、持久化边界、等待和唤醒、取消传播及不确定外部副作用。不要承诺未经证明的全局 exactly-once 执行。

### 组件扩展与环境演进

安装浏览器组件后，编排者在候选脚本导入能力，只授权给指定执行者。能力缺失、版本不兼容或越权须在副作用发生前明确失败。更新脚本时，已有动作按确定版本完成或明确取消。

验收发现和绑定、授权、版本归属、激活失败保留可用环境，以及状态和资源的释放责任。

## 迁移步骤

1. 建立业务价值与测试基线，修正发现、隔离和证据问题。旧 App 的结构断言不能作为未来验收标准。
2. 做“执行与复核”的最小纵向试验，连通脚本执行、一个现有能力适配、持久化事实与观察结果。先验证语义，再定文本语法和实现技术。
3. 加入等待人类、进程重启与外部能力。三个场景验证后，再稳定最小契约。
4. 按场景迁移现有能力，旧接口可短期作为适配入口；提供价值对照、状态处理和回退证据。
5. 替代路径覆盖实际场景后，移除旧清单、安装/宿主接口及相关兼容测试，避免长期维护两套运行主权。

## 待验证的设计问题

- 专用语法还是受约束的现有语言：依据智能体编写/修正成本、可检查性及恢复语义选择。
- 控制流如何持久化：哪些计算可重放，哪些副作用只能根据记录事实接续。
- 扩展能力最小的类型、版本与兼容契约。
- 哪些更新需等待已有工作完成，哪些允许明确迁移。
- 编排者修改自身环境时，如何保留当前授权、恢复入口及人类控制。

用小规模可执行场景和失败试验收敛，不先建一整套平台。语义验收遵循[测试策略](./testing-strategy.md)：有价值的自然语言输出交由测试执行智能体主观判断，禁止用字面匹配替代含义判断。
