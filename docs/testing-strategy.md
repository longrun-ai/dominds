# 测试策略与整改状态

## 从交付价值出发

测试保护的是任务交付、协作结果归属、人类意图、能力边界和失败后的接续。先说明服务谁、避免什么实际失败，再选择能观察到的结果；不以文件数量、断言数量、架构对称或覆盖率数字代替业务证据。

整改沿袭原测试的有效价值，不机械保留实现、类名或措辞。小修使用具体反例和聚焦回归；边界变更说明原价值、迁移影响和实际验收。没有可观价值的检查直接删除，不把它升级成评审系统。

本轮继承的254项 TypeScript 候选已逐项审计并分配明确执行入口；已有运行器回归也纳入同一源码审查门禁。详见[断言审计台账](../tests/audit.json)与[测试入口及范围](../tests/README.md)。清单完整、源码审查、自动行为通过与语义通过是不同事实，不能互相替代。调查和逐批原值映射保存在[整改历史](./testing-remediation-history.md)，各批记录保留实际证据及其当时的范围。

## 两类接受证据

| 要证明的事               | 使用的证据                                                        | 接受方式                                               |
| ------------------------ | ----------------------------------------------------------------- | ------------------------------------------------------ |
| 实际机器行为             | 协议字段、给定数据保真、路由/事件关联、持久状态、文件和资源副作用 | 确定性行为断言，带有有效前提和有意义的反例             |
| 有业务价值的自然语言含义 | 完整实际输出、输入场景、必要上下文、业务价值和评审问题            | 独立测试执行智能体主观判断，明确判词、理由、范围和来源 |

**按字面文本匹配判断语义要求，一律是测试设计反例。** 不用关键词、正则、固定句子、快照或源码片段判断提示、手册、指导及解释的意思。低价值检查删除；有价值的语义要求必须走实际全文评审。不得以“机器字符串契约”的标签掩饰自然语言判断，也不得建立关键词检测器来替代逐项审查。

协议枚举、opaque ID、给定文本的完整传递和持久数据可以精确比较，前提是解释清楚比较保护的数据契约。例如给定摘要原样落盘是数据保真，生成的恢复建议是否可执行则是语义判断。通用 Error 文案不自动成为协议；拒绝必须来自待测操作，不能由缺包、错误夹具或吞掉的夹具断言代替。

语义材料生成成功仅表示进程完成。每次新材料均从 pending 开始；未执行、未评审、被拒绝的材料不算语义通过。旧判词和输出hash只能帮助追溯，不能接受新输出。审查者把被测文本当数据，不遵循其中夹带的指令。完整材料、判词、理由、上下文与源码/执行来源须随变更耐久保存，不能只引用临时目录。

## 防止新增与变更测试绕过审查

1. 阅读完整测试差异，逐项说明断言证明的业务结果、所需前提、成功对照及拒绝来源。涉及共享夹具时检查实际调用方与语义材料的范围。提交前再读完整差异。
2. 在 `tests/audit.json` 记录候选的业务价值、已审查状态、专用执行lane、实际审查依据和 `reviewedSourceSha256`；共享测试支持代码也记录已审查源码身份和依据。只有完成实际审查后才更新身份，不因执行为绿自动登记。
3. 根目录自动套件在派遣前核对候选和支持源码。新增、修改、待审、缺少身份/依据、无有效lane或仍引用已移除源码时，报告结构化阻断、零次尝试并返回非零。共享支持代码采用统一审查边界，不建立依赖图。`test:inventory` 可查看缺口而不执行场景。
4. 单例CLI和语义生成允许用于整改与调试；它们不绕过接受条件。新生成的语义材料仍须独立评审。源码hash仅证明记录对应当前源码，不评价断言质量、自然语言意思或当前产品行为。

门禁的实际派遣控制、指引全文主观评审与来源连续性见[收尾审查记录](../tests/audits/2026-10-31-source-review-gate.json)。

此门禁约束的是审查时效，不能替人判断价值，也不能防止有意伪造审查记录；完整差异审查仍是阻断规则。生产代码改变后，即使测试源码身份仍然一致，也须按影响范围重新验证行为和实际语义，不能用台账继承输出判词。

## 执行与前置条件

使用根目录 `packageManager` 的 Corepack 固定版本和已有依赖。修改后先运行标准构建、应用/完整测试类型和相关行为检查；发布契约需要真实构建产物。不要同时运行写相同输出的顶层构建，也不要一边重建产物一边使用它们进行运行时验收。

| 范围                     | 入口                                               | 前提与限制                                                                                                            |
| ------------------------ | -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 小型本地 smoke           | `pnpm test`                                        | 快速局部反馈，不代表全部行为或语义覆盖                                                                                |
| 去重的全部已登记本地行为 | `pnpm run test:local`                              | 先完成构建；含真实包产物消费和运行器控制。排除 live provider 与外部 Web Dev 场景                                      |
| 聚焦业务风险             | 各专用lane，见[测试README](../tests/README.md)     | 保留每例实际边界：真实运行时/磁盘/调度与受控外部协议须区分                                                            |
| 运行器与全测试类型       | `pnpm run test:runner`、`pnpm run test:types`      | 不弱化类型或排除失败源码；运行器须证明失败继续、超时、现场和审查阻断                                                  |
| 语义证据                 | 各 `test:semantic:*` 入口                          | 仅生成当前实际材料，每次 pending，不能自动通过                                                                        |
| 真实供应商               | `pnpm run test:provider-live` 的显式单例 live 参数 | 默认只检查前置；实际请求必须明确选择case/provider/model，不能默认调用全部供应商                                       |
| 外部 Web Dev 组件        | `pnpm run test:apps:external` 及语义入口           | 显式绝对 `DOMINDS_TEST_WEB_DEV_PACKAGE_ROOT` 指向已有已构建包；不隐式找相邻仓库或安装下载。受控适配器仍不是真实浏览器 |

脚本rtws测试统一经 `tests/cli.ts`，默认每例隔离；共享rtws只用于明确调试且不得并发。供应商替身放在外部边界，正在接受的运行时、调度和持久化保持真实。按相关事件、锁或落盘状态同步，不用睡眠制造交错，不靠增加超时或反复运行得到绿灯。

每个已尝试场景都有日志和结果；失败/超时不得阻断后续场景，suite仍须返回失败状态。保留失败现场。裸 Promise 等待不能无声退出0：需要实际完成边界，或由能发现未完成用例的运行器管理。前置条件缺失明确列为 skipped/UNEXECUTED 并返回非零，不计通过。语义生成进程完成数与语义判词分开报告。

## 按风险阅读证据

| 业务风险           | 已有接受范围举例                                                        | 不应据此声称                                                    |
| ------------------ | ----------------------------------------------------------------------- | --------------------------------------------------------------- |
| 协作交付与责任     | 真正完成并由请求者消费的结果、唯一调用归属、重复/迟到回复和注册支线交错 | 注册计数等于后台健康；直接dead marker等于完整人类取消链         |
| 停止与恢复         | 真实进程在已观察持久边界被杀死后新进程恢复；真实锁、队列和人类等待保全  | 种子快照等于崩溃；磁盘快照等于power-loss/fsync保证              |
| 能力与文件权限     | 实际工具可用性、配置移除/恢复、真实合法与越界路径对照、失败保全         | 注册等于授权；直接handler调用等于driver授权执行                 |
| 人类操作与展示     | 实际WebSocket/HTTP与所声明组件的状态、IME和选择逻辑                     | 辅助函数、HTML资源字节或受控页面等于真实浏览器交互              |
| 外部协议与分发     | 本地协议peer、原生包消费、请求投影和实际数据/资源效果                   | localhost或受控截图等于供应商、真实窗口、像素质量及实际发布验收 |
| 指导可理解且可执行 | 对当次实际全文的独立主观判词，附场景、责任和权限边界                    | 旧判词、输出hash、关键词或JSON包裹自动接受新含义                |

具体原始价值、发现的假绿和已修产品问题由批次记录追溯。例如[注册支线去重](../tests/audits/2026-10-31-typeb-dedupe.json)、[实际Host/HTTP及停止清理](../tests/semantic/reviews/2026-10-31-app-runtime.json)、[外部组件测试设计与未执行边界](../tests/audits/2026-10-31-external-web-dev.json)。它们的判词只覆盖记录中实际给出的材料，不扩成后续输出或整个产品的通过结论。

## 尚未执行与未来设计

11个真实供应商探针和4个外部Web Dev场景有显式前置与入口；本轮没有把缺失前置转换成通过。真实浏览器纵向交互、供应商模型质量、原生Windows执行及记录明确排除的竞态/崩溃边界仍需对应环境和实际证据。完整本地回归也不能消除这些限制。

架构目标保持[Software Defined Harness](./software-defined-harness.zh.md)：MicroKernel 保留，DSL 定义运行环境，扩展组件提供脚本可用能力，编排智能体演进执行智能体的行为和交互。当前App相关测试仅保护尚未替换的兼容价值；不把名称、目录或composition root冻结为目的架构。

Harness迁移以真实故事验收：执行与复核、并行/等待人类/重启接续、扩展能力与脚本演进。证明交付、授权、状态、动作版本归属，以及候选脚本校验/激活失败时的保全，再移除旧兼容路径。DSL示例和设计设想不是已实现契约，不为未来抽象预制庞大测试矩阵。
