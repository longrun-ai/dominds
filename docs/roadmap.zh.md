# Dominds 发展规划（Roadmap）

英文版：[English](./roadmap.md)

## 摘要

Dominds 的目标方向转为 **Software Defined Harness**：保留微内核，以 DSL 定义整个运行环境，由扩展组件提供 DSL 可用能力；编排智能体主导设计并以脚本持续演进各执行智能体的行为和交互。

原来的 Dominds App、App 组合根和 App composition revision 设计被取消。当前实现仍保留相关接口，须按业务场景迁移；它们不是继续建设的目标模型。完整设计见 [Software Defined Harness](./software-defined-harness.zh.md)。

## 最终目标（North Star）

运行环境成为可检查、可版本管理、可由编排智能体演进的程序。微内核维护通用执行和不可绕过的完整性边界，DSL 表达分工、上下文、能力、交互、等待、失败处置和接续，扩展组件实现所需能力。环境并非静态工具配置或固定流程图，也不再需要一个 App 充当组合根。

## Stage 0：价值基线与测试整改

- 从第一性原则说明谁获得什么业务价值、哪些失败必须避免；沿袭分工、接续、人类参与、授权、隔离及可解释性的已有成果。
- 修正测试发现、隔离和失败汇总，核实套件外用例，按业务场景清查覆盖。见[测试设计与全面整改计划](./testing-strategy.md)。
- 禁止以字面文本匹配判断语义；低价值检查删除，高价值语义输出交给测试执行智能体主观评审。新增和修改测试按同一阻断规则审查。
- 当前机制在迁移前继续服务实际场景；不预先把 tellask、team、Reminder、Taskdoc、daemon 或 UI 一一冻结为组件或 DSL 原语。

## Stage 1：DSL 的最小纵向试验

- 先实现“执行与复核”，连通脚本、现有能力适配、持久化事实及业务验收。
- 再验证并行工作、等待人类与重启接续，以及组件扩展和脚本更新三个场景。
- 根据试验确定 DSL 语义、语言形式与能力契约。区分设计草案、可执行实现和未决问题，不先造通用编译器或热更新平台。
- 脚本不得绕过现行权限；安装和导入能力不等于授予。动作归属确定版本，更新明确处置运行中工作。

## Stage 2：按业务场景迁移运行环境

- 让现有能力接入 DSL，必要时通过临时适配；每项迁移提供业务价值对照、状态处理及回退证据。
- 编排智能体依据执行证据修改候选脚本，经校验与微内核控制的激活路径采用新版本。
- 在替代场景成立后，退出旧 App 清单、安装/宿主接口及过时结构测试；不长期维持两套运行主权。
- UI、协作协议与领域能力是否独立为组件，以实际使用与复用边界决定。

## Stage 3：Software Defined Harness 的持续演进

- 稳定由场景证明必要的 DSL 与扩展能力契约，支持可追溯、可恢复的环境演进。
- 建立编排者修改自身环境时的授权、恢复入口与人类控制语义。
- 扩大能力生态及多种交互界面，同时沿袭业务验收和 rtws 隔离。

## 关键原则（跨阶段）

- **第一性原则与价值沿袭**：从需求、约束和失败后果推导方案，保留旧行为的业务价值，不机械保留技术形状。
- **少做无价值工程**：抽象和优化须有具体使用场景与可观察收益；不以通用性、结构对称或推测的性能收益自证。
- **权限与完整性不可绕过**：DSL、扩展和环境更新均受当前执行边界约束。
- **可接续、可解释**：版本、动作、结果与责任能够关联；脚本回退不等于外部副作用回滚。
- **证据真实**：构建、自动行为测试、语义评审和未执行环境分别报告，不把结构或措辞检查冒充业务覆盖。
