# Working on Dominds

## Engineering principles

- Start from first principles: identify the person or agent being served, the business outcome, and the failure being prevented before choosing a technical solution.
- Preserve the value of existing behavior through change. Trace the original need, the useful behavior it produced, and the evidence that the replacement preserves or improves that value. Existing names, classes, package boundaries, and tests are evidence to examine, not requirements to preserve automatically.
- Keep that reasoning proportional to the change: a small fix needs a short explanation and a focused regression; a boundary change needs concrete stories, migration consequences, and acceptance evidence. Do not create a new process framework for routine work.
- Introduce abstractions only when concrete uses need them. A business concern is not automatically a component, toolset, runtime type, or DSL primitive. Prefer a direct implementation until a reusable boundary earns its cost.
- Optimize measured constraints that affect a business outcome. Speculative performance work, generic frameworks, extra indirection, and architectural symmetry do not justify themselves.
- Review changes by asking what becomes better for a user or an executing agent, what existing value could be lost, and which observable result establishes success.

## Architecture direction

- The target is **Software Defined Harness**: retain the **MicroKernel**, define the runtime environment in a DSL, and let extension components add capabilities usable by that DSL.
- An orchestration agent should be able to design and evolve how execution agents work and interact by changing harness scripts. The DSL defines runtime behavior, not just a static tool list or workflow graph.
- The previous **Dominds App / App composition root** design is superseded. Do not extend it as the destination architecture. Existing `DomindsApp`, `main/apps/**`, App Host IPC, and install commands remain current implementation contracts until an explicit migration replaces them.
- Preserve working collaboration, durable execution, human interaction, capability boundaries, and rtws isolation during migration. Do not rename or delete those mechanisms merely to align terminology.
- Design decisions, illustrative DSL examples, implemented contracts, and unresolved questions must be distinguished clearly. See [Software Defined Harness](docs/software-defined-harness.zh.md) and the [roadmap](docs/roadmap.zh.md).

## Repository and development

- `main/`: CLI, integrated backend, dialog driving, persistence, tools, and component hosting.
- `packages/kernel/`: public MicroKernel/shared contracts; `packages/shell/`: shell contracts; `webapp/`: WebUI; `codex-auth/`: authentication/provider support; `tests/`: regression scripts and runners.
- Use the root `packageManager` pin through Corepack. Do not add repository dependencies, change the package manager, or introduce a new test framework merely to perform a local check.
- Standard checks: `pnpm run build`, `pnpm run lint:types`, `pnpm run format:check`, and the relevant behavior tests. Do not run overlapping top-level builds against the same output directories.

## Tests and acceptance

- Test observable business behavior and public effects. Important scenarios include collaboration delivery, interruption and restart, human replies, permissions, and preserved state. Package-layout checks may protect concrete distribution contracts; they cannot substitute for behavior tests.
- Literal text matching to enforce semantic requirements is a test-design counterexample. Do not use keywords, regular expressions, fixed sentences, snapshots, or source snippets to judge the meaning of prompts, guidance, explanations, or other natural-language output. Delete low-value checks of this kind. For valuable semantic requirements, emit the actual semantic text with its scenario and necessary context for a test-execution agent to judge subjectively; retain its verdict, rationale, and evidence. An unreviewed semantic case is pending, never an automatic pass.
- Exact comparisons remain appropriate for actual machine contracts and data: protocol fields, identifiers, persisted state, counts, and observable effects. A machine-contract label must not be used to disguise a natural-language meaning test.
- This is a blocking rule for future tests as well as existing ones. Before accepting any added or changed test, review what each assertion actually proves. Reject literal matching used as a semantic oracle; require a concrete machine-contract justification for text equality. Valuable semantic cases require test-execution-agent review of the emitted evidence and an explicit verdict with rationale. Do not replace this review with a keyword-based semantic-test detector. Check the complete test diff again before committing; pending or rejected semantic review cannot be reported as passing acceptance.
- Preserve semantic review verdicts, rationale, scope, and evidence provenance with the change; a temporary directory alone is not durable acceptance evidence. Output hashes may identify the reviewed material, but cannot judge meaning or automatically accept later output.
- A regression should reproduce a concrete failure before the fix and assert the outcome that matters afterward. Avoid tests that merely repeat the implementation, freeze incidental wording, or enforce the retired App architecture without a remaining compatibility need.
- Use `pnpm test` for the small local smoke suite, `pnpm run test:kernel` for discovered dialog-driver regressions, and `pnpm run test:inventory` to expose tests outside those suites and missing direct TypeScript package-script targets. A green smoke run is not a claim of full coverage.
- `pnpm run test:context` checks generation-boundary eligibility, context-preservation decisions, continuation-body fidelity, retry preparation, real budget consumption/manual continuation, informational exhaustion and global event forwarding. Ingress/context-policy and forwarding cases are component checks; actual queued-message and critical-turn driving is covered by `test:kernel`. `pnpm run test:semantic:context` emits thirty actual guidance/notice cases through three producers for separate subjective review.
- `pnpm run test:configuration` checks team parsing, parsed extension rules against actual file access, capability availability, MCP manual data fidelity, reload and Problems lifecycle through isolated rtws and controlled local MCP peers. `pnpm run test:semantic:configuration` emits their actual diagnostic and manual text for separate subjective review.
- Keep `tests/audit.json` current with each test batch: record business value, assertion review and an explicit execution lane; missing or pending entries remain unaudited. New or materially changed candidate cases require a reviewed entry before acceptance. The ledger records human review scope, never a semantic verdict for fresh output. `test:inventory` exposes these omissions without a keyword-based semantic detector.
- `pnpm run test:manual` checks language/asset selection, skill boundaries, manual visibility and original-content budgets. `pnpm run test:semantic:manual` emits the related actual guidance for subjective review. `pnpm run test:types` checks the entire test directory; its inherited contract errors are tracked explicitly during remediation and must not be hidden by weakening types or exclusions.
- `pnpm run test:semantic:kernel` emits actual reminder context, repeated-call diagnostics, reply errors/expiration, requester guidance, context renewal, registered-assignment updates, tool-outcome uncertainty, declared-dead results, tight-context result visibility, tool-loop transitions, actual queued user interjections, FBR phase/closure guidance and empty-response retry recovery, synchronous ask-back result pointers, reply-delivery rejections and local human interjection/tool-follow-up guidance. It is an explicit evidence lane, not semantic coverage of every discovered kernel case.
- `pnpm run test:filesystem` checks public path/extension permission decisions and real file/link/edit effects through isolated rtws, including preview preservation, pad lifecycle/scope, occurrence-plan ownership and drift guards, scoped team edits and bounded outputs. `pnpm run test:semantic:filesystem` emits actual refusal, preview, link-operation and truncation text for subjective review; its successful generation processes leave semantic acceptance pending.
- `pnpm run test:persistence` checks final disk write-back, thinking replay, requester stacks, canonical/cross-course results, raw unpaired-history preservation, status moves, quarantine and failed-I/O recovery, independent-process reminder owner recovery, active-course reminder writes, fork boundaries and priming state. `pnpm run test:semantic:persistence` emits actual ambiguous-update, occupied-destination, incomplete carryover and quarantine diagnostics for separate subjective review.
- `pnpm run test:recovery` checks owned-process SIGKILL/open-generation restoration, run-control reconciliation, stale-generation cleanup, live reply acknowledgement repair, dialog-lock serialization, human-wait gating and independent-process seeded reply recovery. Preserve explicit resume where required; test snapshot healing and startup reconciliation with independent fixtures. `pnpm run test:semantic:recovery` emits nine actual acknowledgements/diagnostics through four producers for subjective review. The owned-process test covers its observed durable boundary; seeded reply cases do not establish abrupt kill, and neither lane proves power-loss/fsync behavior.
- `pnpm run test:bootstrap` checks local CLI execution, workspace/argv handling, proxy-configuration forwarding, team-validation exit codes, dotenv precedence and environment-tool mutations/refusals. `pnpm run test:semantic:bootstrap` emits actual CLI manuals/reports and tool diagnostics for subjective review. Controlled proxy forwarding and declaration-only MCP validation do not establish working network routing or a running MCP service.
- `pnpm run test:packaging` consumes actual local tarballs in independent directories through native Node and TypeScript with no workspace path aliases. It checks public/private import behavior, source-only and packed type consumers, lossless manifest boundaries, local archive drift, CLI/certificate/HTTP effects and controlled release/cache recovery. Run `pnpm run build` first; pinned pnpm, POSIX `tar` and the existing installed dependency set are prerequisites. Workspace packages must come from tarballs; supplied third-party links are explicit. Release cases execute copied unmodified scripts in owned Git workspaces with controlled npm/pnpm peers; `pnpm run test:semantic:packaging` emits their actual refusals and manifest/drift diagnostics for subjective review. Neither lane proves a registry install, actual publishing/browser authentication, browser interaction or live-provider behavior.
- `pnpm run test:retry` runs three isolated cases for provider failure classification, bounded quirk state, real request-retry timers/events/disk lifetimes and actual two-input Kimi driver recovery. It preserves the three-second empty-response delays and the existing per-case 60-second bound. `pnpm run test:semantic:retry` emits 38 actual policy, UI and recovery cases for subjective review. A component callback reservation does not establish an executed follow-up; only the explicit driver case checks that. SDK transport, live providers and browser interaction remain separate lanes.
- `pnpm run test:projection` runs seven isolated cases for Responses, Chat Completions-compatible and Anthropic history projection, real artifact/native-payload selection, image capability/missing-file controls, result limits and real ripgrep truncation metadata. Image budgets are checked against explicitly declared byteLength data using small distinct GIF files; this does not establish an actual 60MiB request cap. `pnpm run test:semantic:projection` emits twelve actual pairing diagnostics, six Anthropic history projections, nine image cases and seven truncation cases for subjective review. Request projection does not execute tools, repair persisted history, send provider requests or establish image-ingest callback/UI routing; only the explicit ripgrep case invokes that local tool.
- `pnpm run test:compatible` checks Kimi request defaults/schema/usage through the actual SDK and a local HTTP peer, compatible batch handling of incomplete wire JSON, zero-request configuration refusals, real rejected-request capture and stream-parser callback/data contracts. `pnpm run test:semantic:compatible` emits twelve actual configuration, parser, invalid-call and capture diagnostics for subjective review. Stream-parser components are distinct from SDK streaming; localhost peers do not establish live-vendor behavior.
- `pnpm run test:reminders` runs fourteen isolated behavior cases for actual ordering, Main Dialog goal/parallel-role boundaries, body/renderMode preservation, manual guards/stable IDs, controlled post-resolution interleavings, owner failure/stability actual task/agent shared-notice routing/private migration, continuation tagging and pending/wait-state preservation. `pnpm run test:semantic:reminders` has fourteen explicit producers for 125 actual cases: 44 supplied formatter states, ten goal states, eight rendering/receipt/refusal cases, nineteen mutation/owner cases, twenty bilingual shared-routing/migration and owner-refusal cases, and twenty-four continuation/pending-state cases. Pure formatter evidence is support, never an automatic passing test; generation remains pending until independent review. Equivalent metadata object key order must not create a new state revision; arrays retain their order. These cases do not establish actual concurrent drives, browser rendering, pressure/message classification, maintenance execution or restart recovery. Shared cases check actual recipient IDs, runtime-guide envelopes, persisted pending prompts/triggers and root scheduling flags. Explicit fixture acknowledgment clears observed queue state; it does not establish LLM consumption. Continuation snapshots and persisted child histories are declared inputs; pending-state zero counts must remain scoped to the current dialog and preserve real human/dependency waits.
- `pnpm run test:daemon` runs nine isolated local process/runner cases for start/stop, one-shot owner exit events, saved terminal snapshots, reminder stability, stream selection/waits and identity-safe recovery. `pnpm run test:semantic:daemon` emits twenty-four bilingual actual receipts, snapshots and diagnostics for subjective review. Request observation is not waiter-installation acknowledgment; continuous child output is explicitly controlled. Registry reset is not an independent-process restart. The runner exits with its daemon, so retained snapshots establish actually saved last-known data, not unseen final bytes or an unobserved numeric exit code. Platform process-tree behavior remains a separate lane.
- `pnpm run test:presentation` checks six local data/component cases: timestamp ordering, generation metadata from real workspace configuration, bounded tracing logs, run-control projection, IME-key classification and teammate selection. `pnpm run test:semantic:presentation` has two support producers for eighteen actual model-label/tooltip and bilingual context-title cases. The formatters are subjective evidence, not automatic passing tests; supplied usage/threshold facts and pure selectors do not establish live-provider measurement, pressure classification, browser rendering or real input-method interaction.
- Put new shared test helpers under `tests/helpers/`, rather than alongside discovered kernel entry points; helper-only modules must not be counted as passing tests. Semantic evidence generation reports pending review and is separate from automatic behavior acceptance.
- Mock provider behavior at the external boundary; keep runtime, persistence, and scheduling real when those are under test. Live-provider probes, external-component integration, packaging, browser interaction, and platform-specific checks need separate, explicit test lanes.
- Run script-rtws cases through `tests/cli.ts`; default to isolated rtws. Never run shared rtws cases concurrently. Preserve failing evidence when investigating. Synchronize on relevant events or state instead of sleeps; do not hide a failure by raising timeouts or retrying until green.
- A suite must report all attempted cases and return a failure status for failed or timed-out cases. Report skipped prerequisites and unexecuted scenarios explicitly; do not count them as passes.
- Use the [test strategy and remediation plan](docs/testing-strategy.md) to guide broader changes. Fix nearby defects when understood, with scope and regression evidence; keep unrelated rewrites separate.

## Markdown Link Pre-commit Lint

- Before committing any change that can affect Markdown navigation, lint the complete set of documentation Markdown tracked by this repository, not only the changed files. Use the repository's own `git ls-files -- '*.md'` results as the candidate source set; never scan a parent workspace, sibling repository, dependency tree, or generated output as source documentation.
- Dominds documentation must remain self-contained. After decoding and normalizing a local target relative to its canonical source document, every local document link must remain within this repository root. A path that happens to resolve through an enclosing integration workspace is still a failure.
- Use a Markdown-aware checker with local fragment support, such as Lychee with `--offline --include-fragments`. Check local file targets and Markdown heading fragments, but do not request or fail on the reachability of `http`, `https`, or other network links.
- Markdown-formatted runtime prompts, personas, templates, and test fixtures are not documentation merely because their filenames end in `.md`. Keep any source exclusions narrow and role-based, and never use them to conceal a broken documentation link. Canonicalize tracked Markdown symlinks and lint each underlying document once so an alias path does not invent false relative-link failures.
- Ignore link-like examples inside code spans and fenced code blocks. Do not add broad path, fragment, or status exclusions to hide a real missing target. This rule currently remains a pre-commit agent check only; do not add CI workflows, Git hooks, or repository dependencies for it without separate authorization.
