# Working on Dominds

## Engineering principles

- Start from first principles: identify the person or agent being served, the business outcome, and the failure being prevented before choosing a technical solution.
- Preserve the value of existing behavior through change. Trace the original need, the useful behavior it produced, and the evidence that the replacement preserves or improves that value. Existing names, classes, package boundaries, and tests are evidence to examine, not requirements to preserve automatically.
- Keep that reasoning proportional to the change: a small fix needs a short explanation and a focused regression; a boundary change needs concrete stories, migration consequences, and acceptance evidence. Do not create a new process framework for routine work.
- Introduce abstractions only when concrete uses need them. A business concern is not automatically a component, toolset, runtime type, or DSL primitive. Prefer a direct implementation until a reusable boundary earns its cost.
- Optimize measured constraints that affect a business outcome. Speculative performance work, generic frameworks, extra indirection, and architectural symmetry do not justify themselves.
- Review changes by asking what becomes better for a user or an executing agent, what existing value could be lost, and which observable result establishes success.

## Architecture direction

- The target is **Software Defined Harness**: retain the **MicroKernel**, define the runtime environment in a DSL, and let extension components add capabilities usable by that DSL.
- An orchestration agent should be able to design and evolve how execution agents work and interact by changing harness scripts. The DSL defines runtime behavior, not just a static tool list or workflow graph.
- The previous **Dominds App / App composition root** design is superseded. Do not extend it as the destination architecture. Existing `DomindsApp`, `main/apps/**`, App Host IPC, and install commands remain current implementation contracts until an explicit migration replaces them.
- Preserve working collaboration, durable execution, human interaction, capability boundaries, and rtws isolation during migration. Do not rename or delete those mechanisms merely to align terminology.
- Design decisions, illustrative DSL examples, implemented contracts, and unresolved questions must be distinguished clearly. See [Software Defined Harness](docs/software-defined-harness.zh.md) and the [roadmap](docs/roadmap.zh.md).

## Repository and development

- `main/`: CLI, integrated backend, dialog driving, persistence, tools, and component hosting.
- `packages/kernel/`: public MicroKernel/shared contracts; `packages/shell/`: shell contracts; `webapp/`: WebUI; `codex-auth/`: authentication/provider support; `tests/`: regression scripts and runners.
- Use the root `packageManager` pin through Corepack. Do not add repository dependencies, change the package manager, or introduce a new test framework merely to perform a local check.
- Standard checks: `pnpm run build`, `pnpm run lint:types`, `pnpm run format:check`, and the relevant behavior tests. Do not run overlapping top-level builds against the same output directories.

## Tests and acceptance

- Protect observable business behavior: collaboration delivery, interruption/restart, human replies, capability boundaries, and preserved state. A regression reproduces a concrete failure and checks the useful outcome after the fix. Layout/schema checks protect only their explicit contracts; they do not establish runtime behavior. Do not freeze the retired App architecture without a remaining compatibility need.
- Literal matching to enforce a semantic requirement is a test-design counterexample. Never use keywords, regexes, fixed sentences, snapshots, or source snippets to judge the meaning of prompts, manuals, guidance, explanations, or other natural-language output. Delete low-value checks of this kind.
- For valuable semantic requirements, emit the complete actual text, scenario, necessary context and review questions for an independent test-execution agent to judge subjectively. Preserve its explicit verdict, rationale, scope and evidence/source provenance durably with the change. Temporary output alone is insufficient. Unreviewed, pending, rejected or unexecuted semantic cases cannot be reported as passing acceptance. A fresh generation always starts pending; old verdicts and output hashes never accept new meaning.
- Exact comparisons are appropriate for actual machine contracts and data: protocol fields, identifiers, supplied opaque payloads, persisted state, counts and observable effects. Explain the concrete contract a text equality protects. Do not relabel natural-language meaning as a machine contract.
- These are blocking rules for existing and future tests. Review what every added or changed assertion proves, and inspect the complete test diff again before committing. Reject semantic literal oracles; do not replace this review with a keyword-based detector. Keep reviewed source identities, business value, explicit execution lanes and durable review references current in `tests/audit.json`, including shared test support. The root suite source-review gate rejects missing, pending and stale review records; its hashes identify reviewed source, never assertion quality or semantic acceptance. Update an identity only after the actual review, never automatically because execution is green. Direct debugging and semantic generation are not acceptance shortcuts.
- Mock external provider behavior at the boundary; keep runtime, scheduling and persistence real when they are under test. Expected rejection must come from the operation under test, not missing dependencies, malformed fixtures or swallowed fixture assertions. Pair boundary refusals with otherwise valid inputs and meaningful successful controls.
- Put shared test helpers in `tests/helpers/`, outside discovered executable entry points. Helper-only modules and semantic producers are not automatic passing behavior tests. Do not add dependencies, a framework or generic test machinery merely for a local check.
- Run script-rtws cases through `tests/cli.ts`; default to isolated rtws. Never run shared rtws cases concurrently. Preserve failing evidence. Synchronize on relevant events/state instead of sleeps; do not hide failures by raising timeouts or retrying until green. Async scenarios need an observable completion boundary: an unresolved Promise must not exit zero and become a pass.
- Suites report every attempted case and return nonzero for failure or timeout. Declare prerequisites and report skipped/unexecuted scenarios explicitly; never count them as passes. Keep local controlled behavior, packaging, external components, live providers, real browser interaction and native platform execution as separate scopes. A smoke pass is not full coverage, and source review is not execution.
- Use `pnpm test` for the small smoke suite, `pnpm run test:local` for deduplicated registered local behavior, `pnpm run test:runner` for runner controls, `pnpm run test:types` for the entire test directory and `pnpm run test:inventory` for source-review/discovery gaps. Do not weaken types or exclude failing cases. Consult the [test entry points and scope](tests/README.md) and [test strategy](docs/testing-strategy.md) for focused lanes, prerequisites and semantic evidence commands. Fix understood nearby defects with scope and regression evidence; keep unrelated rewrites separate.

## Markdown Link Pre-commit Lint

- Before committing any change that can affect Markdown navigation, lint the complete set of documentation Markdown tracked by this repository, not only the changed files. Use the repository's own `git ls-files -- '*.md'` results as the candidate source set; never scan a parent workspace, sibling repository, dependency tree, or generated output as source documentation.
- Dominds documentation must remain self-contained. After decoding and normalizing a local target relative to its canonical source document, every local document link must remain within this repository root. A path that happens to resolve through an enclosing integration workspace is still a failure.
- Use a Markdown-aware checker with local fragment support, such as Lychee with `--offline --include-fragments`. Check local file targets and Markdown heading fragments, but do not request or fail on the reachability of `http`, `https`, or other network links.
- Markdown-formatted runtime prompts, personas, templates, and test fixtures are not documentation merely because their filenames end in `.md`. Keep any source exclusions narrow and role-based, and never use them to conceal a broken documentation link. Canonicalize tracked Markdown symlinks and lint each underlying document once so an alias path does not invent false relative-link failures.
- Ignore link-like examples inside code spans and fenced code blocks. Do not add broad path, fragment, or status exclusions to hide a real missing target. This rule currently remains a pre-commit agent check only; do not add CI workflows, Git hooks, or repository dependencies for it without separate authorization.
